# Security Model

> Owner: agentic-core maintainers
> Last updated: 2026-05-23
> Scope: cross-cutting security posture for `agentic-core` and every app it scaffolds

This document is the canonical reference for the security posture of `agentic-core` and the mini-apps it generates. It defines the threat model, the per-app isolation invariants every generated app must satisfy, and the operational procedures around the encrypted admin keystore.

**Current default.** New apps use Google sign-in and agent keys. They do not use Logto or the admin keystore. Read "Google Sign-In Apps" below for their rules. The eight invariants and the keystore sections apply to Logto apps (`--auth-provider logto`) and to the automated Logto setup.

If you are about to:

- Add a new generated-app field that touches credentials, or
- Change the bootstrap pipeline's interaction with Logto / Railway / GitHub, or
- Hand the scaffolder to an agent for the first time

then read this document end-to-end first.

---

## Threat Model

`agentic-core` historically assumed a single trusted human author. The first Logto apps share a Logto tenant with cross-app SSO and a single high-privilege `agentic-core-admin` Management API client that was reachable from runtime env vars.

That posture is fine while a human writes every line of code. It is **wrong** the moment a coding agent starts writing, deploying, or running app code on the same surface, because:

| Risk | Why it matters under agent authorship |
|------|--------------------------------------|
| **Transitive npm/pip CVE** in a single deployed app | Agent-generated package lists drift faster than human-curated ones; one compromised transitive dep in `app A` can read its process env and exfiltrate any credential it finds. |
| **Prompt injection via user-submitted data** in a deployed app | An agent-deployed app may accept user data and feed it back into an LLM. Standard prompt-injection attacks become exfiltration paths for env-resident secrets. |
| **Careless generated code** | An agent may inadvertently log secrets, write them to a debug endpoint, or commit them. Multiple shallow mistakes compound. |
| **Shared SSO across apps** | If app A's session cookie or refresh token leaks, the attacker silently has app B and app C as well — even if B and C are otherwise clean. |
| **Shared Management API client at runtime** | The `agentic-core-admin` M2M client is the highest-value credential in the system. Possession of it lets an attacker create, modify, or delete any Logto application, resource, role, or user. If it lives in any deployed app's env, the blast radius of a compromise is the entire platform. |

### Containment Strategy

Two architectural moves contain the worst-case compromise to one app:

1. **Per-App Token Isolation** (the 8 invariants below) — every app gets its own M2M client, its own API resource, its own SPA, and its own per-app Logto user. A stolen credential from app A cannot be replayed against app B because the `aud`, `client_id`, and user identity all differ.
2. **Admin Keystore Off-Runtime** — the `agentic-core-admin` Management API client is moved out of every deployed app's env entirely. It lives only in an encrypted keystore on the operator's machine, decrypted only for the duration of a `create-app` invocation, and never written to disk in plaintext or shipped into any container.

The result: a compromised deployed app can damage itself. It cannot pivot to siblings, and it cannot escalate to platform-wide control.

## Per-App Token Isolation (8 Invariants)

Every app generated by `agentic-core create-app` MUST satisfy all eight invariants. These are day-1 architectural constraints, not aspirational goals. Track C's tests enforce them mechanically; this section is the human-readable contract.

Variant applicability is summarized at the end of this section.

### Invariant 1: Per-app M2M client

Each app gets its own Logto Machine-to-Machine application. `LOGTO_M2M_APP_ID` and `LOGTO_M2M_APP_SECRET` are unique per app and are **never** shared across apps.

- Provisioned by `agentic-core/bootstrap/logto.py` during scaffold.
- Written only into the new app's own Railway env vars under the slug-prefixed naming convention (e.g., `NOTES_M2M_APP_ID`).
- Rotation of one app's M2M secret has zero effect on any other app.

### Invariant 2: Per-app API resource

Each app's API resource indicator is `https://<slug>.<domain>/api` (the operator sets the domain with `--platform-domain` or `PLATFORM_DOMAIN`; there is no default), with its own scope set. Every token minted for app A carries `aud = https://<A>.<domain>/api` exactly. Server-side middleware on app B rejects any token whose `aud` does not match its own resource.

A stolen `notes` M2M token **cannot** be replayed against `habits` because the audience check fails closed.

(The `/api` suffix lives at the end — not as an `api.` subdomain — because the resource is bound to the app's deployed origin rather than a separate API hostname. The format is set by ``agentic_core/bootstrap/logto.py``'s ``provision_app``.)

### Invariant 3: Per-app SPA + per-app user

Each app gets its own Logto Single-Page Application (for human login), plus its own dedicated Logto user under the convention `app_<slug>`, with hyphens changed to underscores (for example `app_habits`). There is **no cross-app silent SSO** because there is no shared user identity to log in with.

If an attacker steals app A's session cookie, they get app A, period. They do not get app B even if both apps are mounted in the same browser.

### Invariant 4: No shared admin client at runtime

The `agentic-core-admin` Management API client lives **ONLY** in the encrypted keystore. Specifically:

- Filesystem (default): `~/.agentic-core/admin.keystore.json`
- Filesystem (override): the `--admin-keystore` path or `AGENTIC_CORE_ADMIN_KEYSTORE`

It is **NEVER** written into:

- A generated app's `.env` or `.env.example`
- A generated app's Railway env vars
- A generated app's `Dockerfile`, `start.sh`, or any container artifact
- The bootstrap state file (`.bootstrap-state.json`)
- Logs, stdout, stderr, or error envelopes
- Any shared shell `.env` file (e.g. a global `.agentic-apps.env`)

Mechanical check (Track C tests): grep every rendered template file for `LOGTO_MANAGEMENT*` and the literal admin secret — both must come up clean.

### Invariant 5: One secret store per app

Each app's secrets live in its own dedicated Railway project. There are **no** Railway "shared variables" spanning projects.

The agent platform enforces a per-project allowlist on top, so that an agent invoking the Railway CLI cannot accidentally write a secret into a project it does not own.

### Invariant 6: Per-app rotation

Rotating one app's M2M secret, SPA credentials, or API resource touches no other app's credentials. There are no compound rotations and no platform-wide downtime windows. Rotation procedure for app X:

1. In Logto admin console, rotate the M2M secret on app X's M2M client.
2. Update `<SLUG>_M2M_APP_SECRET` in app X's Railway env vars.
3. Redeploy app X. Done.

Apps Y and Z are untouched and continue serving traffic.

### Invariant 7: Audit-friendly token use

Server-side FastAPI middleware logs the app slug, the M2M client ID, and the actor sub on every validated request. This produces a per-request audit trail that supports later anomaly detection (cross-app reuse, off-hours bursts, requests from unexpected IPs).

The nightly anomaly scanner itself is a follow-up — out of scope for v1. The logging surface is in scope and lands with Track B's middleware extensions.

### Invariant 8: No long-lived secrets in source

The template ships a `.gitignore` that covers:

```
.env
.env.local
.env.production
.env.*.local
*.keystore.json
*.last-good
*.bak
*.bak.*
.bootstrap-state.json
```

The template's `.env.example` contains **only** placeholder strings:

- `__SET_IN_RAILWAY__` for production-injected secrets
- `__GENERATED_BY_SCAFFOLD__` for values the bootstrap fills in at provision time

An entropy-gate test (`tests/unit/test_template_env_example_entropy.py`) renders the template. It asserts that the rendered `.env.example` contains no run of 32 or more characters from `[A-Za-z0-9+/=_]`. Real keys, hashes, and JWTs match that pattern; the placeholders are shorter. The test covers `.env.example` only, not every rendered file.

### Variant Applicability Matrix

Not every invariant applies to every variant; here is the canonical mapping:

| Invariant | `full` | `lightweight-api` | `static-dashboard --with-auth` | `static-dashboard --no-auth` |
|---|---|---|---|---|
| 1. Per-app M2M client | Required | Required | N/A | N/A |
| 2. Per-app API resource | Required | Required | N/A | N/A |
| 3. Per-app SPA + user | Required | N/A | Required | N/A |
| 4. No admin client at runtime | **Required** | **Required** | **Required** | **Required** |
| 5. One secret store per app | Required | Required | Required | Required |
| 6. Per-app rotation | Required | Required | Required | N/A |
| 7. Audit-friendly logging | Required | Required | N/A | N/A |
| 8. No long-lived secrets in source | **Required** | **Required** | **Required** | **Required** |

Invariants 4, 5, and 8 are universal. The others apply only where the corresponding surface exists.

### Google Sign-In Apps (`auth_provider=google`)

New Render apps use Google sign-in instead of Logto. A Google-mode app meets the eight invariants as follows:

| Invariant | How a Google-mode app meets it |
|---|---|
| 1. Per-app machine credential | Agent keys exist only in the app's own `AGENT_CREDENTIALS` (SHA-256 hashes). Each key acts for one person (`google:<sub>`) and reads only unless the operator grants write. |
| 2. Per-app audience | One Google OAuth client per app. The backend accepts an ID token only when `aud` is exactly the app's `GOOGLE_CLIENT_ID`. No Google token is ever accepted as an API credential. |
| 3. Per-app human session | The session cookie is signed with the app's own `SESSION_SECRET`, is HttpOnly and SameSite=Lax, and on https is Secure with the `__Host-` prefix. Only emails in `AUTH_ALLOWED_EMAILS` get access. |
| 4. No admin client at runtime | Unchanged. Google mode uses no admin client at all. |
| 5. One secret store per app | The Google and agent key settings load only from the app's own `.env` and process environment, never from the shared `~/.agentic-apps.env`. On Render they are `sync: false` service variables; Render generates `SESSION_SECRET`. |
| 6. Per-app rotation | Rotate the Google client secret, `SESSION_SECRET` (signs everybody out), or one agent key without touching another app. |
| 7. Audit-friendly logging | One JSON line per auth decision: app slug, auth method, user ID, agent key ID, decision. Never an email, a token, or a key. |
| 8. No long-lived secrets in source | `.gitignore` adds `*.agent-key`. The operator tool writes keys to a new 0600 file and never prints them. |

Fail-closed rules:

- While a required Google setting is missing or invalid, every protected route and every `/auth/*` route return 503 `auth_not_configured`. A missing or short `SESSION_SECRET` gives the cookie signer a random per-process key, never a constant.
- When a request has an `Authorization` header, only an agent key can pass. A failure never falls back to the session cookie.
- A malformed or duplicate `AGENT_CREDENTIALS` entry rejects every machine request (503 `agent_credentials_invalid`) and leaves browser sign-in working.

Known limits: the operator cannot revoke one session alone. To end a person's browser access, remove the email from the allowlist. Rotating `SESSION_SECRET` ends all sessions. The allowlist does not apply to agent keys, so also remove every `AGENT_CREDENTIALS` entry whose `actor` is that person. There is no mobile client yet. Design and setup: `docs/google-auth-setup-guide.md`.

## Admin Keystore Lifecycle

The `agentic-core-admin` Logto Management API client is the highest-value credential in the system. This section is the operator's contract with it.

### Format

- **`eth-account` v3 JSON** (scrypt KDF + AES-128-CTR cipher).
- A standard, widely used on-disk format (the Ethereum v3 keystore), read and written by a maintained library.
- Generated and consumed by `agentic_core/bootstrap/keystore.py`.

### Location

| Environment | Default path |
|---|---|
| Default | `~/.agentic-core/admin.keystore.json` |
| Override (for example on a shared server) | `--admin-keystore PATH` flag, or `AGENTIC_CORE_ADMIN_KEYSTORE` env var |

Resolution rule: the `--admin-keystore` flag wins over the env var, which wins over the default path.

Keep the file outside the repo and outside any container bind-mount. It is never copied into a deployed app image.

### Passphrase Transport (CRITICAL — R1)

The passphrase that unlocks the keystore is passed to `agentic-core create-app` via:

- **Interactive (local dev):** stdin prompt — `getpass.getpass("Admin keystore passphrase: ")`.
- **Agent or CI invocation:** file descriptor — `--passphrase-fd N`. The caller writes the passphrase to a transient pipe and passes the read end, for example as fd 3.

**NEVER pass the passphrase via environment variable.** Specifically: there is no `AGENTIC_CORE_ADMIN_PASSPHRASE` env var. Environment variables are readable from `/proc/<pid>/environ` by any same-UID process for the entire scaffold duration (minutes), which is a far larger attack window than the kernel pipe used by `--passphrase-fd`.

This is a hard rule. Reviewers and code-review automation will reject any patch that re-introduces a passphrase env var.

### Lifetime in Memory

- Decrypted **only** during the lifetime of a single `agentic-core create-app` (or `agentic-core admin ...`) invocation.
- The decrypted key is held in process memory for the duration of the scaffold's Logto Management API calls (typically < 60 seconds).
- After scaffold completion, the bootstrap code performs **best-effort process-memory clearing**: zeroing out the `bytes` buffer holding the decrypted secret before the variable goes out of scope. Python does not give us a hard guarantee here (garbage collector + copy-on-immutable semantics), hence "best-effort"; the keystore lifetime bound and the no-env-var rule are the load-bearing controls.
- The decrypted key is **never** written to disk in plaintext, **never** included in the JSON output envelope, **never** logged, and **never** persisted to the `.bootstrap-state.json` resume file.

### One-Time Setup (`agentic-core admin init-keystore`)

The operator runs this once to encrypt the `agentic-core-admin` Logto Management API credential into a passphrase-protected keystore.

```
agentic-core admin init-keystore \
  [--keystore-path PATH] \
  [--m2m-id ID] \
  [--passphrase-fd N] \
  [--logto-endpoint URL] \
  [--yes]
```

Behavior:

1. Read the M2M App ID from (in priority order): `--m2m-id` flag → `LOGTO_M2M_APP_ID` env var → interactive `typer.prompt`.
2. Read the M2M App Secret from (in priority order): `LOGTO_M2M_APP_SECRET` env var → interactive `getpass` prompt. **There is no `--m2m-secret` flag** — flags land in argv and leak via `ps`, shell history, and `/proc/<pid>/cmdline`.
3. Read the keystore passphrase from `--passphrase-fd N` (agent or CI pipe path) or via two `getpass` prompts (interactive: typed twice with exact-match confirmation).
4. Print a non-secret summary (target path + M2M App ID only — never the secret) and ask `Proceed? [y/N]` unless `--yes` was passed.
5. Two-phase verification: encrypt + atomic-write the keystore (mode 0600), then decrypt-test it for byte-equality with the original secret, then mint one real Logto Management API token with the decrypted credential — only then declare success.
6. Print an operator instruction: delete `LOGTO_M2M_APP_SECRET` from `.env` and `unset LOGTO_M2M_APP_SECRET` in the parent shell. Keep `LOGTO_M2M_APP_ID`: it is not secret, and `create-app` preflight needs it.

After this, the encrypted keystore is the only place the secret lives.

### Keystore Backup Procedure (R17)

The keystore is the single point of failure for the entire `agentic-core` bootstrap. Without it, you cannot create new apps until you manually recreate the Logto admin M2M client (see Keystore Loss Recovery below).

**Back it up immediately after `init-keystore`.** Recommended procedure:

1. **Copy the encrypted keystore to a second physical location.** The file is already encrypted with your passphrase; you do not need to re-encrypt it. Suggested locations:
   - 1Password / Bitwarden secure document attachment
   - Encrypted external drive (full-disk encryption such as APFS-Encrypted or LUKS)
   - A second machine you control, in its own `~/.agentic-core/` directory

   ```
   cp ~/.agentic-core/admin.keystore.json /Volumes/EncryptedBackup/agentic-core-admin.keystore.json
   ```

2. **Store the passphrase separately from the keystore.** The passphrase belongs in a password manager (1Password, Bitwarden, `pass`). It does **not** belong in:
   - Shell history (`~/.zsh_history`, `~/.bash_history`)
   - A `.env` file
   - Notes apps that sync to cloud services in plaintext
   - The same vault entry as the keystore backup itself (defeats the purpose of separation)

3. **Verify the backup is restorable.** On a clean machine (or in a throwaway directory):
   ```
   cp /Volumes/EncryptedBackup/agentic-core-admin.keystore.json /tmp/test.keystore.json
   agentic-core admin verify-keystore --admin-keystore /tmp/test.keystore.json
   # enter passphrase from password manager when prompted
   rm /tmp/test.keystore.json
   ```
   A non-zero exit means the backup is corrupt or the passphrase is wrong. Fix it now, not the day you need it.

4. **Re-back up after every rotation.** If you rotate the admin M2M secret in Logto (or generate a new keystore), the old backup is stale. Repeat steps 1–3.

### Keystore Loss Recovery

If you lose the keystore (disk failure, accidental deletion, ransomware) **and** the backup is unrecoverable **and** you have forgotten the passphrase, the `agentic-core-admin` credentials are unrecoverable as far as the keystore is concerned. You must manually recreate the admin client.

Manual recovery procedure:

1. **Log into the Logto Admin Console** as a human administrator (the Logto root admin user, not via the `agentic-core-admin` M2M).
   - URL: see `docs/logto-setup-guide.md` for the current admin console URL.
2. **Revoke the old admin M2M client** (if it still exists). Go to **Applications** → `agentic-core-admin` → **Settings** → **Delete application**. This prevents any leaked copy of the old credentials from being used.
3. **Create a new Machine-to-Machine application** named `agentic-core-admin`:
   - Type: Machine-to-Machine
   - Name: `agentic-core-admin`
   - Description: `Bootstrap admin client — used by agentic-core create-app only. Never deploy to any app runtime.`
4. **Assign the Management API role.** Go to **Roles** → select the role with `all` scope on `https://default.logto.app/api` (or create one named `Logto Management API access` if it does not exist) and assign it to the new `agentic-core-admin` application.
5. **Copy the new Client ID and Client Secret** out of the Logto admin console.
6. **Run `agentic-core admin init-keystore`** to encrypt them into a fresh keystore. Pick a new, strong passphrase. Store it in your password manager **before** moving on.
7. **Re-do the backup procedure above** for the new keystore.

You do **not** need to touch any deployed app during this recovery. Per Invariant 4, no deployed app holds admin credentials, so the loss of the admin keystore does not affect any running service. It only blocks new `create-app` invocations until step 7 completes.

If you have lost the passphrase but **still have the keystore file**, the file is useless without brute-forcing scrypt — which is computationally infeasible for any passphrase of reasonable strength. Treat this as keystore loss and follow the procedure above.

### Operator Guidance — Passphrase Storage

The passphrase is what makes the keystore useful and what makes its theft catastrophic. Treat it accordingly:

- **Store in a password manager.** 1Password, Bitwarden, `pass`, or equivalent. Generate a random 4–6 word passphrase (Diceware) or a 24+ character random string.
- **Never in shell history.** Do not type the passphrase as a CLI argument that bash will record. The interactive stdin prompt and `--passphrase-fd N` flag are the only correct paths.
- **Never in a `.env` file.** This defeats the entire reason for the keystore.
- **Never reused.** This passphrase is the only thing protecting the platform's highest-value credential. It should be unique.
- **Rotated if exposed.** If the passphrase is ever typed in a recorded session, pasted into a chat, or otherwise exposed, run a fresh `init-keystore` with a new passphrase and re-back up.

## Operator Responsibilities Summary

This is the human-facing checklist. Print it, or keep it pinned.

| Responsibility | Frequency | Where documented |
|---|---|---|
| Keep the admin keystore backed up to a second location | After every `init-keystore` or rotation | This document, Keystore Backup Procedure |
| Store the passphrase in a password manager, not in shell history | Continuous | This document, Operator Guidance |
| Periodically verify the keystore backup is restorable | Quarterly | This document, Keystore Backup Procedure step 3 |
| Never paste the admin M2M secret into any deployed app's env | Continuous | This document, Invariant 4 |
| Pass a dedicated `--railway-workspace` (for example `agent-sandbox`) for any agent-initiated scaffold | Per invocation | `agentic-core create-app --help` (`--railway-workspace`) |
| Use `--passphrase-fd N` (or interactive stdin) — never an env var | Per invocation | This document, Passphrase Transport |
